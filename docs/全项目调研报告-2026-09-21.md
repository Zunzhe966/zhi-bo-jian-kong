## 三、⚠️【逻辑问题 C】最严重的一条：「打开文件夹」永远找不到转写文字

### 前端以为的路径 vs 实际落盘位置

`desktop/src/stash.js:231`：

```js
export function itemStashDir({ kind, name, url, paths }) {
  const downloads = trimSlash(paths && paths.downloads)   // ← 只用 downloads
  if (!downloads) return ''
  if (kind === 'live') {
    return `${downloads}/${platformDirName(url)}/${cleanDirName(name)}`
  }
  return `${downloads}/短视频/${safeDirName(name)}`
}
```

**但 `paths` 里明明有 `fupan_output` 键（实测 `zunzhe-core paths`）：**

```
downloads      = /Volumes/A区/尊者产物/downloads        ← 视频在这
fupan_output   = /Volumes/A区/尊者产物/fupan_output     ← 转写文字/复盘笔记在这
```

**⇒ `itemStashDir` 完全无视 `paths.fupan_output`。**

### 后果（这正是用户问的「打开文件夹打开去哪儿了？这也没有啊」）

| 计划 | 前端"打开文件夹"指向 | 实际内容 | 判定 |
|---|---|---|---|
| 直播 | `downloads/{平台}/{主播名}` | 视频 ✅ 但**不含转写** | ⚠️ 只到一半 |
| 短视频 | `downloads/短视频/{name}` | 视频 ✅ 但**不含转写** | ⚠️ 只到一半 |
| **转写文字** | **没有任何入口指向 `fupan_output/`** | `.转写.txt` 等 | ❌ **无入口** |

**而这直接违反用户的产品要求**：
> 「不同的直播、短视频，分别由自己的地方，也按主播分类，
>  然后**文字和视频是在一起的**，只是两种东西」

**现在是两棵分离的树：`downloads/`（视频）和 `fupan_output/`（文字）。**

> 📌 附注：还有一个矛盾 —— `stash.js` 给直播算的是 `downloads/{平台}/{主播}`，
> 但复盘产物实际落在 `fupan_output/{name}/{场次}/`。
> 两套命名规则（`platformDirName`+`cleanDirName` vs `pipeline.py` 的 `record_name/media.stem`）
> **可能算出不同的目录名**，即使都指向 `downloads/` 也不一定命中。

## 四、逻辑与设计审计：哪些设计是对的

### ✅ 4.1 三层分离 —— 对的

```
Electron(界面) → Rust daemon(主控) → Python(工具)
```
- 界面只管展示和发命令（`cli()` 单通道）
- Rust 管调度、状态、数据库（唯一权威）
- Python 只做"工具"（转写/监控），被 Rust spawn

**理由充分**：Rust 保证 daemon 长期稳定（24×30 长跑），Python 保证
faster-whisper / yt-dlp 这类生态现成可用。

### ✅ 4.2 程序与数据分离 —— 对的

```
程序：/Volumes/A区/尊者监控直播短视频/
数据：/Volumes/A区/尊者产物/
```
`paths.rs` 统一定义，更新软件永不碰数据。**这是正确的工程决策。**

### ✅ 4.3 直播源用 ini 文件而非数据库 —— 对的（我之前误判为 bug）

`db.rs:476` 写明：

> 「**直播监控的唯一权威是 `URL_config.ini`**。旧库曾把视频空间地址也写入 anchors」

**设计理由**（实测验证）：
- ini 支持 `#` 行首暂停语义（不删除、灰显）
- 用户可直接编辑
- 数据库 `live_states` 只存**运行状态**（`is_live` / `consecutive_fails`）

**⇒ `anchors` 表为空是"故意的"**（防止视频源脏数据混入）。**但空表应清理。**

### ✅ 4.4 MCP 风险分级 —— 好的安全设计

43 个工具按 6 个风险级分类，`mcp_audit.rs` 记录每次调用（`mcp_calls` 表 70 条）。
**这是"智能体可控"的必要护栏。**

### ✅ 4.5 IPC 白名单 —— 对的

`main.cjs:813` 的 `ALLOWED_CLI_COMMANDS`（28 项）+ **明确报错而非静默失败**：
```js
if (!ALLOWED_CLI_COMMANDS.has(cmd)) {
  console.warn('[cli] 拒绝未在白名单内的命令:', cmd)
  return Promise.reject(new Error(`不允许的命令: ${cmd}`))
}
```
**实测：前端没有调用任何白名单外命令**（0 个越权）。

### ✅ 4.6 静态检查结果 —— 干净

| 检查项 | 结果 |
|---|---|
| Rust `TODO`/`FIXME`/`HACK` | **0 个** |
| Python 吞异常 (`except: pass`) | **0 处** |
| `unwrap()` 密集处 | 全在 `#[cfg(test)]` 测试块内 |
| 注释密度 | db.rs 8% / service.rs 11% / scheduler.rs 13% |
