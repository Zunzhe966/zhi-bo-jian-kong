# 统一动作层与可迁移数据根设计

日期：2026-09-18
状态：待用户审阅

## 1. 目的

本项目当前把程序代码、配置、数据库、日志、运行态文件和产物混在同一套目录语义里。前端按钮、CLI 子命令、MCP 工具又是三套各自维护的入口，导致同一个能力在不同入口存在、缺失或命名不一致。用户看到的直接后果是：

- 数据目录可以改，但数据库仍可能落回源码根。
- 日志有两套位置，排障时不知道哪份是真的。
- “自动转写”开关只写配置，已存在的视频没有可见的“立即转写/重新转写”动作。
- 发布二进制可能与源码命令集不一致。
- MCP 对本项目暴露 0 个 Bagua 控制入口。

本设计给出统一数据根、统一动作注册表和第一批真实动作的契约。它不直接修 bug；实现必须在本设计审阅通过后，按单独的实现计划执行。

## 2. 当前证据

### 2.1 数据位置

当前 `config/config.ini` 的 `[路径设置]`：

```ini
产物根目录 = /Volumes/A区/尊者产物
短视频下载目录 =
复盘输出目录 =
数据库文件 =
```

当前实际路径：

| 数据 | 当前实际落点 | 证据 |
|---|---|---|
| 产物根 | `/Volumes/A区/尊者产物` | `config/config.ini` |
| 主数据库 | `<源码根>/zunzhe-core.db` | `paths.rs:283-284` |
| WAL | `<源码根>/zunzhe-core.db-wal`，实测约 3.0 MB | `ls -l` |
| 日志 | `<源码根>/logs/`，实测约 26 MB | `ls -l`、`du` |
| 旧默认产物目录 | `~/Documents/尊者产物` | 实测存在空壳 |

`paths.rs` 的文档明确说数据库默认值是 `<项目目录>/zunzhe-core.db`，这与“运行数据不得留在源码里”冲突。

### 2.2 日志

当前存在至少两套日志语义：

- `<源码根>/logs/`
- `~/Library/Logs/zunzhe/`

launchd 的 stdout/stderr 路径与 daemon 自己打开的日志路径不一致时，同一进程的日志会被拆到不同位置。日志根目录没有进入 `StoragePaths`，因此界面、CLI、doctor 也无法统一回答“日志到底在哪”。

### 2.3 入口与动作

源码中当前有：

- Rust CLI：`cli.rs` 的 `Command` 枚举，实测 48 个变体。
- MCP：release 二进制 `tools/list` 实测返回 41 个工具。
- Electron IPC CLI 白名单：`main.cjs` 实测 28 个允许的命令。
- 前端页面：4 个主标签，另有托盘菜单和应用菜单入口。

已知的入口缺口：

- `process_media` 是真实 MCP 工具，CLI 也有 `process`，但前端没有“立即转写/重新转写”按钮。
- 前端只有“录制/下载完成后自动转写”开关；保存开关不会处理已经存在的视频。
- 已实测：当前 release 二进制和隔离 target 重新构建的 debug 二进制都实际接受 `mcp` 入口，但两者的 `--help` 都声明并列出 `extension`。Git `HEAD` 中的 `cli.rs` 也把命令定义为 `extension`。也就是说，运行时入口、帮助文本和源码声明三者已经漂移；两者虽然都能返回 41 个工具，但 MCP 接入文档不能放心按 `extension` 配置。
- `control_list` 显式传入本项目根时返回 0 个控制入口；同一个总账默认指向八卦项目时返回 9007 个入口。

### 2.4 Bagua 薄控制面

八卦项目的控制面适配器已经支持非八卦项目通过项目根 `.神经/控制面.json` 登记控制入口。读取规则是：

- 文件固定为 `<项目根>/.神经/控制面.json`。
- 顶层 JSON 为 `{"控制": [...]}`。
- 每个条目的控制类型限定为 `CLI`、`Python脚本`、`extension工具`、`可执行功能`、`API`。
- `CLI`、`Python脚本`、`可执行功能` 必须有 `源码路径`。
- `允许执行` 默认是 `false`，必须显式登记。

因此本项目不需要伪造一套独立控制协议；应把自己的动作注册表生成或校验为这份薄清单，并作为 Bagua、MCP 与 UI 的共用权威来源。

## 3. 目标

### 3.1 唯一可迁移数据根

引入一个用户可自由选择的数据根 `DATA_ROOT`。默认值可以是用户主目录下的应用数据目录，但程序目录内不得存放运行时数据。

建议布局：

```text
<DATA_ROOT>/
  config/
    config.ini
    fupan_config.ini
    URL_config.ini
    视频监控列表.ini
    监控偏好.json
    桌面偏好.json
  data/
    zunzhe-core.db
    zunzhe-core.db-wal
    zunzhe-core.db-shm
  logs/
    zunzhe-core.log
    zunzhe-core.uptime.log
    zunzhe-core.audit.log
  run/
    daemon.pid
    daemon.lock
    heartbeat
    sockets/
  downloads/
    short-video/
    live/
  fupan_output/
    <主播>/
      <场次>/
        *.转写.txt
        *.转写.json
        *.知识点.json
        *.复盘笔记.md
        clips/
  covers/
  recordings/
  credentials/
    bilibili_browser_cookies.txt
    douyin_browser_cookies.txt
    bilibili_user_cookies.txt
```

约束：

- `DATA_ROOT` 必须可以指向任意本地卷，包括机械硬盘、外置盘和新建目录。
- 选择数据根时不得要求用户选中程序目录。
- 选择数据根时不得要求目录里已经有 `config/config.ini` 或 `zunzhe-core.db`。
- 数据库、日志、运行态文件、Cookie、录像、下载、转写产物和复盘产物都必须落在 `DATA_ROOT` 内。
- 程序目录只保留程序、源码、构建产物和只读资源。

### 3.2 单一动作注册表

建立一个机器可读的动作注册表。每个动作至少包含：

```json
{
  "行动身份": "video.transcribe",
  "显示名": "转写这个视频",
  "所属区域": "视频详情",
  "输入契约": {"file_path": "string", "anchor_name": "string"},
  "输出契约": {"task_id": "string", "status": "queued"},
  "副作用": ["写任务队列", "启动 daemon"],
  "执行入口": {"kind": "mcp", "name": "process_media"},
  "风险级别": "写入",
  "允许执行": true,
  "源码路径": "zunzhe-core/src/extension.rs",
  "说明": "对已有录音或视频立即入队转写和复盘"
}
```

该注册表必须：

- 由单一数据源生成或校验。
- 至少生成三层视图：MCP 工具、CLI 子命令、前端按钮/IPC。
- 为每个前端按钮标明其真实副作用。
- 为每个 mutation 动作标明是否需要确认、是否可重试、是否可撤销。
- 禁止用“只改配置但文案暗示已执行”的假动作。
- 禁止在 UI 中出现无法调用的占位按钮。

### 3.3 Bagua 薄控制面

从同一动作注册表生成 `<项目根>/.神经/控制面.json`，并在刷新总账后验证：

- `control_list(项目根=当前项目)` 返回本项目登记的动作，而不是 0。
- 每个可见动作的身份、输入契约、源码路径、允许执行状态与注册表一致。
- 只读动作和写入动作必须可区分；删除、服务停止、清理类动作默认要求确认。

### 3.4 真转写

必须保留并暴露一个真实的“立即转写”路径：

1. 用户在视频详情、最新视频卡片或复盘页点击“转写这个视频”。
2. UI 调用动作注册表中的 `video.transcribe`。
3. 后端验证文件在本项目可信媒体根内。
4. 后端把 `process` 任务写入 daemon 队列。
5. daemon 的复盘 worker 调用 Python AI 工具层执行转写、提炼和切片。
6. UI 显示任务状态，并在完成后显示转写文本、知识点和复盘笔记。

验收必须证明：点击后产生新的任务记录，worker 实际启动 Python 流水线，产物文件真实出现；不能只验证配置项被保存。

## 4. 非目标

本设计不包含：

- 用占位邮箱、占位 Cookie 或伪造结果来证明通知、B站、抖音链路可用。
- 未经用户确认重启正在运行的 daemon。
- 为了兼容旧行为而继续把数据库或日志默认写进源码根。
- 把 AI 工具层重写成 Rust。
- 删除历史数据；迁移只允许复制、校验后切换，不覆盖源。

## 5. 设计

### 5.1 路径契约

新增逻辑层 `DataRoot`，职责只有：

- 解析用户选择的数据根。
- 校验数据根可读写。
- 派生所有受管路径。
- 维护数据根指针。
- 提供配置、DB、日志、run、downloads、fupan、covers、recordings、credentials 的统一路径。

`StoragePaths` 不再自行决定数据库默认位置，而是完全由 `DataRoot` 派生。Rust、Python、Electron 必须读取同一个数据根指针，不能各自推导。

数据根指针的候选顺序：

1. 显式环境变量。
2. 用户选择后保存的指针文件。
3. 打包态的用户数据目录。
4. 开发态的项目配置。

如果指针指向不存在的数据根，行为必须是明确失败或明确的“创建新数据根”，不能静默回退到源码根。

### 5.2 数据迁移

迁移采用两阶段：

1. 复制并校验：复制旧配置、DB、日志、产物到新数据根，计算校验结果。
2. 切换指针：只有校验通过后才写指针文件；源数据保持不动。

迁移必须处理 SQLite WAL：

- 迁移前执行 checkpoint，或复制主库、WAL、SHM 三者。
- 迁移后运行完整性检查。
- 不允许直接移动正在被 daemon 打开的数据库。

### 5.3 动作注册表与适配器

建议新增一个纯数据格式的动作注册表，以及三个薄适配器：

- MCP 适配器：把注册表投影成 MCP 工具定义。
- CLI 适配器：把注册表投影成 CLI 子命令。
- UI/IPC 适配器：把注册表投影成前端动作与 IPC 白名单。

适配器只做契约转换，不实现业务逻辑。真实副作用仍然进入现有深模块，例如 `watchlist`、`download`、`pipeline_bridge`、`service`。

### 5.4 日志与可诊断性

日志根目录必须成为 `StoragePaths` 的一等字段，并同时提供给：

- daemon
- CLI `paths`
- MCP `status`
- Electron `open-path`
- doctor

日记类、审计类、心跳类日志应统一在日志根下，并保留轮转。任何界面“打开日志目录”动作都必须打开同一个路径。

### 5.5 失败任务的可解释性

任务失败必须在任务记录中保留 `last_error`，不能只依赖日志文本。UI 的失败列表应能显示：

- 任务类型
- 关联视频或直播
- 失败阶段
- 最后错误
- 尝试次数
- 重新转写/重试入口

### 5.6 前端结构

保留 4 个主标签：

- 直播监控
- 视频监控
- 复盘笔记
- 运行日志

但把动作层级收敛：

- 每个视频卡片和视频详情必须有“转写这个视频”。
- 已有时长的卡片或仍有转写失败记录的地点必须有“重新转写”。
- 每个主播或博主卡片只有一个“打开文件位置”动作和一个“设置”动作。
- 不再用多个含义相近的按钮表达同一个文件位置。
- “打开日志目录”只是一个动作，且必须打开统一日志根。

## 8. 验收标准

### 8.1 数据根

- 新建一个空目录作为数据根后，配置、DB、日志、run、下载、复盘产物和 Cookie 全部落在该目录。
- 源码根不再新增 `zunzhe-core.db`、WAL、SHM、日志或产物。
- 关闭并重启后，Rust、Python、Electron 读到同一个数据根。
- 换盘后，旧数据可以迁移，迁移前后数据可校验。

### 8.2 动作注册表

- 41 个现有 MCP 动作全部进入注册表。
- 每个前端可见按钮都有注册表条目和真实副作用说明。
- 同一动作在 MCP、CLI、UI 中的身份一致。
- mutation 动作只在临时数据根验证，不写生产数据。

### 8.3 Bagua

- `control_list(项目根=本项目)` 返回登记动作。
- 只读动作与写入动作可区分。
- 删除、服务停止、清理类动作需要显式确认。

### 8.4 转写

- 在 UI 中点击“转写这个视频”后，数据库出现对应 `process` 任务。
- daemon 复盘 worker 实际执行 Python 流水线。
- 转写文本、知识点或复盘笔记至少产生一种真实产物。
- 失败时 UI 能看到 `last_error`，并能发起重新转写。

### 8.5 发布一致性

- 源码、CLI、MCP 工具列表、Electron 入口和打包产物使用同一套命令名。
- release 二进制与源码构建的命令集一致。
- 发布前自动检查命令集与动作注册表是否漂移。

## 9. 实施顺序

1. 建立数据根契约与路径解析测试。
2. 建立动作注册表，并先生成只读视图。
3. 迁移现有配置、DB、日志和产物到新数据根。
4. 修复 MCP 入口命名与发布产物一致性。
5. 登记 `.神经/控制面.json` 并验证 Bagua 控制入口。
6. 在前端加入真实的“转写这个视频”和“重新转写”动作。
7. 修复任务错误可见性。
8. 统一日志根与 `tail_logs`、doctor 的语义。
9. 在临时数据根跑全链路验证，再决定是否切换生产。

## 10. 风险与未决问题

- 迁移正在运行的 daemon 数据库需要短暂停止或在线备份；必须在用户批准后执行。
- B站、抖音和邮箱的真实端到端验证需要用户提供授权；没有授权时只能验证队列与错误处理，不能伪造成功。
- 当前工作区有大量未提交改动，实施时必须按文件隔离并保留用户已有修改。
- 当前 `PROJECT_GOAL.md` 和 `项目现状.md` 仍包含旧路径，实施前应统一到一个当前有效的路径说明。

## 11. 需要用户批准的决定

本设计建议采用：
