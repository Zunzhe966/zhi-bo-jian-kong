# 尊者直播监控 Rust 重构 — 目标模式（北极星）

> 本文件是 Rust 重构的恢复锚点。任何会话开始、上下文丢失、目标被压缩时，
> 先读本文件 + 项目根 `PROJECT_GOAL.md` + `git status`，再按“当前阶段”继续。

## 一、最终目标（验收标准）

1. **长期稳定可用**：`zunzhe-core` 可 24 小时 × 30 天持续运行，不崩溃、
   不丢状态、崩溃后重启自恢复（SQLite 持久化 + 任务队列重放 + 日志）。
2. **原子模块化**：每个最小功能是一个独立 crate 模块（config / model / db /
   platform / video_library / download / notify / pipeline_bridge / scheduler /
   training_data / cli），模块间只通过公开 trait + 结构体契约连接，像电话线一样
   可插拔、可单测、可替换。
3. **改动不破坏**：任何模块改动都必须先跑全量回归（`cargo test` + 集成测试），
   已验收功能回归失败 = 不允许提交。
4. **能力对齐**：Rust 逐个重写旧 Python 能力：直播监控/录制调度、发布视频监控、
   历史视频浏览与选择性下载、转写/提炼/切片复盘桥接、邮箱通知、视频库、训练数据
   JSONL、CLI/MCP 命令集。
5. **平台**：macOS 优先可用，Windows/Linux 可编译运行，未来可上云服务器。
6. **简单可用**：个人用户不用懂内部实现，桌面端/CLI 一键操作；不出现
   “用着用着崩溃”“监控断了没人管”“状态丢失”等基础稳定性问题。

## 三、接口契约（冻结）

- CLI 每条命令输出一行 JSON，命令名与 Python 版一致：
  `status / add-live / remove-live / list-live / check-live / add-video /
  remove-video / list-video / check-videos / download-video / blogger-videos /
  video-library / export-training-data / email-status / email-setup /
  test-email / start / stop / notes / process`
- SQLite 表：`anchors / videos / notify / tasks`，字段与 Python `video_library.py`
  对齐，`videos.downloaded` 是唯一“已下载”事实源。
- 平台适配器返回统一 `VideoMeta { id, platform, url, title, cover,
  published_at, duration }`，不泄漏平台私有字段。
- 复盘桥接通过子进程调用 Python 工具层（faster-whisper / LLM / ffmpeg），
  Rust 只负责调度、状态、通知与产物索引。

## 四、防回归规则（每次改动必须）

1. `cd zunzhe-core && cargo fmt --check && cargo clippy --all-targets && cargo test`
2. 新增模块必须带 `#[cfg(test)]` 单测；涉及跨模块的加集成测试。
3. 全量回归通过后才 `git add` / commit；commit 信息注明模块（如 `feat(zunzhe-core): M1 config`）。
4. 不允许把已验收模块“顺手改坏”：若修改共用接口，先更新契约文档再实现，
   并跑全量测试。

## 五、稳定性验收（24×30）

- daemon 循环用 `tokio::select!`，任何单个任务 panic 不拖垮主循环；
  顶层安装 panic hook + 崩溃日志；直播检查与视频检查各自独立任务，
  `JoinError` 只记日志，主循环继续下一轮。
- SQLite 每次写操作事务化；崩溃后重启读取 DB 恢复主播/视频/任务/通知状态。
- 服务守护：发现进程不在则拉起（launchd KeepAlive / 桌面端 watchdog）；
  日志轮转（保留 5 份）；心跳文件 30 分钟内必须刷新，否则 `status` 判为
  不健康；磁盘满/ffmpeg 缺失等通过 `doctor` 可诊断。
- 冒烟测试：`run-daemon --once` 与 `run-daemon --duration 30s` 不崩；
  `SIGTERM/SIGINT` 优雅退出并清理 pid 文件；长期稳定性由真实机器持续运行验收。

视频监控已对齐 Python 旧版首轮基线语义：首次检查某位博主只记录已有视频，不通知、
不下载；后续轮次只对新视频通知/下载。后续长期稳定性由真实机器持续运行验收；
平台风控（B站 412 / RSSHub 403）在未配置 Cookie 时可能仍会失败，Rust 适配器
会返回明确错误而不是静默失败；当前真实机器已有桌面端浏览器授权 Cookie
（`fupan_output/run/bilibili_browser_cookies.txt`），投稿列表与下载会自动注入。

直播监控 M17：Rust daemon 已接管直播检测与 ffmpeg 录制，支持 B站原生
（room_init + playUrl/getRoomPlayInfo）和自定义 m3u8/flv 流地址；录制会话写
SQLite（live_sessions），崩溃重启后可恢复；录制结束后自动调用 Python 复盘流水线。
`start`/`stop` 兼容层在 Rust daemon 运行时不重复启动 Python 直播服务，避免双录；
`stop` 只停 Rust daemon 与录制进程，不自动拉起 Python 服务（避免“停止”反而启动服务）。

稳定性加固：所有平台适配器/直播检测请求统一 20 秒超时；daemon 每轮 tick
直播检查与视频检查并行、整体最多 70 秒，超时强制 abort 本轮子任务再进入下一轮，
避免上一轮子任务残留导致重复检查/下载；`--duration N` 用独立 watch 通道按时退出，
不会因单次网络阻塞而无限运行。

新增稳定性修复（已通过 37 个测试 + fmt + clippy）：

- yt-dlp 查找以项目根 `.venv` 为基准，跨目录运行也不依赖当前工作目录。

新增稳定性交付（已通过 39 个测试 + 3 集成契约测试 + fmt + clippy + release 构建）：
- daemon 单实例锁：`fupan_output/run/zunzhe-core.lock` 用独占文件锁贯穿整个
  daemon 生命周期，重复 `run-daemon` 直接报错退出；pid 文件只由锁持有者

  再拉起，watchdog 能恢复“假健康/僵死 daemon”。

新增稳定性交付（已通过 41 个测试 + 3 集成契约测试 + fmt + clippy + release 构建）：

新增稳定性交付（已通过 44 个测试 + 3 集成契约测试 + fmt + clippy + release 构建）：

## 十四、RSS 监控失败显式化与日期规范（最新）

## 三十五、配置文件原子写入防损坏（当前）

- 新增 `patch_ini_file_is_atomic_and_leaves_no_temp_files`，锁定更新成功、无

## 三十七、外部子进程树统一回收，避免超时残留 ffmpeg/Electron

上一轮只保证 `tokio::Child::kill_on_drop(true)`，它最终调用标准库 `Child::kill()`，
只向直接父进程 PID 发信号。`yt-dlp`、复盘 Python 或 Electron 在运行中再拉起
ffmpeg/浏览器子进程时，下载或复盘一旦超时，父进程会被杀，但孙进程可能继续占
用文件、网络和 CPU；长期运行会累积孤儿 ffmpeg，进而导致资源耗尽、录制停止或
文件句柄卡住。

本轮新增统一进程生命周期模块 `src/process.rs`：

- `ManagedChild::spawn` 在 Unix 上把外部命令放入独立进程组，Windows 保持现有
  taskkill 语义。
- `wait` / `wait_with_output` 在超时时先记录并保存子进程 PID，再对整个进程组
  发送 SIGTERM，等待 500ms 后 SIGKILL；非法 pid 直接跳过，避免负进程组误杀。
- 接入下载器 `yt-dlp`、B站 Electron 提取、B站 ffmpeg 合流、复盘 Python
  `fupan.pipeline`、多平台直播 Python 桥接、B站投稿列表 yt-dlp 兜底。
- 新增 `timeout_also_kills_grandchild_process`：用 `sh -c 'sleep 30 & wait'`
  制造孙进程，超时后断言孙进程也被进程组信号回收，防止只杀直接父进程的回归。

长跑审计发现任务队列的去重语义有残留缺口：

- `db::enqueue_task` 只查 `pending` 状态，但注释声称“failed 也会去重”；
  实际 `failed` 是重试耗尽后的终态，worker 不会自动再认领，用户再次点击

- 更隐蔽的是 `download::enqueue_process` 把 `failed`/`done` 都算“已有任务”
  并返回旧 id。这意味着同一媒体文件失败后，用户手动重新运行复盘会拿到
  一条永远 failed 的旧任务，worker 不再执行，用户看到“已入队”却没结果。

- `db::enqueue_task` 对同一 `kind+url` 只在 `pending/processing` 时去重；
  `failed` 视为可重新入队，创建新任务回到 pending，供 worker 再次执行。
- `download::enqueue_process` 对 `pending/processing/done` 去重，避免同一
  媒体文件重复转写/切片；只有 `failed` 视为可重新入队，手动重试会创建新任务。
- 新增 `failed_task_can_be_re_enqueued_for_manual_retry` 回归测试，锁定

## 九十一、修复主日志静默与调度假健康（最新）

24×30 审计时发现真实 daemon（pid 30156）的 `logs/zunzhe-core.log` 最后一行
停在本地 16:52，之后 1.5 小时没有任何 tick 日志；但 `uptime.log` 仍在每分钟
追加，心跳文件也在 18:22 更新，外部 doctor 一度把卡死的调度误判为健康。

### 根因

- 该 daemon 由 Codex 环境拉起，进程环境继承 `RUST_LOG=warn`，而 tracing 默认
  只输出 `info` 及以上；`info!` 的“tick ok / 冷却跳过”全部被过滤，日志看起来
  “停写”，实际是日志级别问题，不是磁盘/轮转故障。
- 心跳文件由主循环维护，独立 uptime 任务只写日志；若主循环在不受 70 秒超时
  保护的阶段卡住，外部 `doctor`/`ensure-services` 仍会看到“进程活着 +
  心跳新鲜”的假健康，无法自动恢复。

### 修复

- 调度器新增独立看门监督器：按 `interval*2` 检查心跳新鲜度，超过阈值记录
  `warn` 并触发优雅退出；外部 watchdog/`start_rust_daemon` 拿到锁后会自动
  拉起新实例，消除“进程活着但实际停摆”的假健康。
- 主循环等待阶段改为每 60 秒刷新一次心跳，保证 15 分钟间隔的正常运行不会被
  新监督器误判；新增回归测试
  `heartbeat_watchdog_threshold_covers_wait_and_tick`。
- `service` 新增公开只读 `heartbeat_age_secs`，供监督器与后续诊断复用。
- 定位到真实启动脚本 `scripts/start-rust-daemon.sh` 已显式设置
  `RUST_LOG="${RUST_LOG:-info}"`，launchd plist 也固定 `RUST_LOG=info`；
  由 Codex/桌面进程直接 spawn 时继承 `warn` 的边界场景，重启后以脚本/plist
  的标准环境运行。

## 第 125 轮：任务认领候选窗口跳过退避修复（2026-08-15）

24×30 审计发现 `claim_pending_task_by_kind` 的候选窗口有真实缺口：查询只按
`ORDER BY id LIMIT 20` 取前 20 条，再在 Rust 里过滤退避。若前 20 条都处于
退避期，排在第 21 条的新任务（`attempts=0`）会被整轮漏掉，worker 必须等
退避任务到期后才能继续消费；大量任务集中失败时，新任务会长时间卡在队列里，
表现为“点了但没执行”。另外，两条并发入口同时认领同一条任务时，抢占失败的
那次直接返回 `None`，也会让后面可认领的任务多等一轮。

本轮修改：

- 候选查询改为 `ORDER BY CASE WHEN attempts = 0 THEN 0 ELSE 1 END, id`：
  新任务永远排在退避任务前面，跨过整个退避窗口也能被立即认领；退避任务之间
  仍按 id 保持先来后到。
- 并发抢占失败（`rows_affected()==0`）不再直接返回 `None`，继续检查候选里
  的下一条，避免整次认领因一次竞争而漏掉后续任务。
- 新增 `fresh_task_outside_backoff_window_is_still_claimed` 回归测试：先造
  20 条刚失败、处于退避期的任务，再造第 21 条新任务，断言新任务仍能立即
  被认领，且 20 条退避任务全部保持 pending。
