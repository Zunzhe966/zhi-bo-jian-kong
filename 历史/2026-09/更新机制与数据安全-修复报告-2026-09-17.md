# 更新机制与数据安全 —— 修复报告

日期：2026-09-17
范围：尊者直播监控（Electron 界面 + Rust daemon）
结论：**「更新一次数据像丢一次」的根因已定位并修掉；「点一下就更新」已做出来并实测跑通。**

---

## 一、根因：界面会静默用一份空数据库

`desktop/electron/main.cjs` 的 `runtimeDir()` 负责回答「数据到底在哪」。原来的逻辑是：
依次探测几个候选目录，**全都探测失败时静默回退**到
`app.getPath('userData')`（即 `~/Library/Application Support/尊者直播监控/`）。

问题是那里**正好躺着一份 2026-08-26 的空 `zunzhe-core.db`**（61440 字节）。
于是：

1. 界面读到空库 → 列表全空 → 看起来「数据全没了」；
2. 界面接着在那个目录新建配置；
3. daemon 再写一套新库。

**凭空长出一份分叉的数据**，而你真正的那份一直安安静静躺在移动硬盘上没动过。

实测证据：修复后应用已正常启动多次，那份空库的
`mtime` 仍是 `Aug 26 12:01:48 2026`，**一个字节都没被碰过**。

## 三、更新功能：只换程序，永不碰数据

设计前提只有一条：**程序和数据在物理上就是分开的。**

- 程序：`/Applications/尊者直播监控.app`
- 数据：`<数据目录>`（config、zunzhe-core.db、fupan_output、downloads）

更新源 = `<数据目录>/releases/`，**全离线，不需要任何服务器**。
把新版本丢进这个文件夹，界面上点「检查更新」就行。

认可三种投放形式：

```
releases/尊者直播监控-1.2.2.zip      ← 推荐，体积小
releases/尊者直播监控.app            ← 直接放目录也可以
releases/1.2.2/尊者直播监控.app      ← 按版本分文件夹也可以
```

版本号是唯一权威，取包内 `Info.plist` 的 `CFBundleShortVersionString`，必须比当前版本高。

更新动作本身：解压 → 暂存到 `/Applications/.zunzhe-update-*`（同卷才能原子改名）→
adhoc 签名 → `renameSync` 原子替换，旧包改名 `.zunzhe-old-<时间戳>`。
**全程不触碰数据目录。**

## 四、这一轮额外挖出来的真 bug

### 4.1 Electron 改写的 fs 让 `fs.rmSync` 删不掉应用包

- 症状：应用里的清理函数**从来没成功过**，每更新一次就在 `/Applications`
  里留一份 **288MB** 的残骸。内盘越用越少，却查不出谁占的。
- 我一度误判成 macOS 13+ 的「App 管理」TCC 在拦非公证应用。**不是。**
- 真因：Electron 会改写主进程的 `fs`，把**任何含 `.asar` 的路径**当成压缩包的
  虚拟目录。于是 `fs.rmSync(包目录, {recursive:true})` 递归到
  `Contents/Resources/app.asar` 时，认定它是个目录、去调 `rmdir`，
  内核直接回 `ENOTDIR: not a directory`。
- 修法：删包一律走新的 `rmrf()`，内部用 `spawnSync('/bin/rm', ['-rf', ...])`
  绕开被改写的 fs。
- 顺带确认的好消息：**应用完全有权限给自己的包改名**（实测 `renameSync` 成功）。
  这正是原子替换依赖的那一步，所以更新链路本身是通的，坏的只是清理。

### 4.2 打包时把整个 `node_modules` 塞进了 asar

`files` 里没排除 `node_modules`，asar 里有 11304 个条目、**76,375,383 字节**。
但主进程的 `electron/*.cjs` 只 require
`assert / child_process / crypto / electron / fs / module / os / path / url` 和本地文件，
运行时**完全不需要**它们（antd / react 已经被 vite 内联进 `dist/`）。

加 `"!node_modules/**"` 之后：

| | 改前 | 改后 |
|---|---|---|
| `app.asar` | 76,375,383 字节 | **3,272,961 字节**（缩小 23 倍） |
| 整个 `.app` | 375M | **288M** |

另外 `_bili_test.cjs` 这类测试文件原来也被打进包，一并排掉。

## 八、更正：「每次都打包出个新软件」这件事，我错在哪

用户的原话是：「我要的是更新，不是每次都打包」「你给我弄出百个软件啊」「正常软件是怎么更新的」。

### 8.1 正常软件的三种更新方式

| 方式 | 怎么做的 | 谁在用 | 离线可行吗 |
|---|---|---|---|
| **全量替换程序目录** | 下载完整新版包，原地把程序文件夹换掉，重启。安装位置不变、数据目录不碰 | Chrome、VS Code、Zoom、Slack、所有 Electron 系 | **可行** |
| 增量补丁 delta patch | 只下载变化的字节，本地与旧版做差分合并 | Windows Update、部分 Chrome 更新 | 不可行（要服务器为每一对版本准备差分包） |
| 应用商店托管 | 系统负责分发、替换、回滚 | App Store、Microsoft Store | 不可行（要开发者账号 + 上架） |

本项目做的就是**第一种**，方向是对的（离线、不依赖服务器，这是既定要求）。

### 8.2 我实际做错的两件事

1. **一天之内发了三个版本号**（1.2.0 / 1.2.1 / 1.2.2）。
   每修一点就发一版，就是在制造「一堆几乎一样的软件」。
   正确节奏：一批改动改完 → 测完 → **只发一次**。
   这条规矩已写进 `scripts/publish-release.sh` 头部。
2. **旧包没清**。更新源里躺着 1.2.1 + 1.2.2 两个 120M 包（共 240M）。
   正常软件的更新目录不会堆历史包。

### 8.3 修法（已实测）

- `publish-release.sh` 现在**自动把比新版本低的旧包移进废纸篓**（不是永久删）。
  实测：故意造 `尊者直播监控-1.1.0.zip` 和 `1.0.0/尊者直播监控.app` 两个旧样本进去，
  跑一次发布，两个都被清走，只剩最新的 1.2.2。
  护栏也验过：**版本比新版本高的包不会误删**（造 9.9.9 进去，脚本打印「保留」）。
- 发布后顺手**清掉构建产物里那份重复的 .app**（要留用 `--keep-build`），
  免得工作目录里又躺一个 288M 的「第二个软件」。
- 加了**压缩包自检**：`unzip -Z1` 必须能查到 `.app/Contents/Info.plist`，
  否则报错退出，不会把一个坏包放进更新源。
- 新增开关：`--keep-old`（保留旧包）、`--keep-build`（保留构建产物）、`--list`（只看更新源）。

### 8.5 「旧的到底放哪去了」——如实回答

- **1.1.0**：我第一次换包时用了跨卷 `mv`，报 `EXDEV` 失败，随后 `ditto` 直接覆盖上去。
  已不可找回（它功能更弱：没有数据目录守卫、没有更新能力）。
- **1.2.0**：被更新流程改名成 `.zunzhe-old-<时间戳>`，然后 1.2.2 启动时按设计清掉。
- **1.2.1 的 zip**：本轮清盘时移进了废纸篓。

清理本身是设计行为，**但我事先没有讲清楚「旧版会被清掉」，是我的沟通失职。**

### 8.6 一个容易误会的点：数据库 sha256 为什么会变

`zunzhe-core.db` 的 sha256 在 18:43 之后发生了变化 —— **这不是更新流程干的，是 daemon 自己写的。**
daemon 每 900 秒一轮 tick（日志实测：18:44、18:59 两轮，`zunzhe-core.db-wal` 时间戳 18:59 吻合），
每轮都会更新 live_states / monitor_baseline 等表。

判断依据：
- `publish-release.sh` 全文只写 `$RELEASES`（`rm -f $ZIP`、`ditto ... $ZIP`、
  `dispose $entry`、`cat > $RELEASES/说明.txt`）和 `dispose` 构建产物，
  **没有任何一行写数据目录的其它位置**。
- 两次更新都在**秒级窗口内**做了前后 sha256 对比，结果都是一字不差。

结论：**要判断更新有没有动数据，必须在更新的秒级窗口内前后对比**，
拿半小时前的老快照去比会被 daemon 的正常写库误导。

### 8.7 顺手修掉的一个脚本 bug（bash 3.2 陷阱）

`echo "旧版本 $v：$base"` 在 macOS 自带 bash 3.2 下会把 `$v` 打成空、全角冒号变乱码
（实测输出 `旧版本 ��1.0.0`）。原因是 bash 按字节解析变量名，
全角字符的第一个字节被吞进变量名。改成 `${v}` / `${base}` 解决。
自检办法：用正则扫 `\$[A-Za-z_]\w*` 后面紧跟 `ord() > 127` 的字符，扫到就改。

**别用 `grep -c '，' file` 判断标点有没有被吞** —— 它只能数总量，
本轮就是先数出「全角逗号 18 个」而误判为没事，孤立跑一次才暴露。
