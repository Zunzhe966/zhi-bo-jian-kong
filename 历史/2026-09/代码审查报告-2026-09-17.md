## 一、结论先行

这次查出 **3 个 P0、4 个严重、10 个中等、9 个轻微**。最要紧的不是某个函数写错了，而是三条结构性问题：

## 三、严重（会直接导致功能不可用）

### S-1　「打开日志目录 / 打开录制目录」按钮在打包版必然失效

`desktop/electron/main.cjs:412-418`：

```js
const isTrustedPath = (p) => {
  ...
  const allowed = [path.resolve(PROJECT_DIR), path.resolve(app.getPath('userData'))]
  return allowed.some((root) => abs === root || abs.startsWith(root + path.sep))
}
```

打包态下 `PROJECT_DIR = path.resolve(__dirname,'..','..')` = `/Applications/尊者直播监控.app/Contents`
而按钮要打开的路径来自 `status.paths`：

```json
{ "logs": "/Users/zhangxuetao/Projects/尊者监控直播短视频/logs",
  "recordings": "/Users/zhangxuetao/Projects/尊者监控直播短视频/downloads" }
```

这两个路径**不在白名单里** → handler 返回字符串 `'拒绝：仅允许打开项目/用户数据目录内的路径'`，不抛异常，界面把它当成功 → **点了完全没反应**。

**修法**：白名单改成 `[runtimeDir(), app.getPath('userData')]`。

### S-2　视频监控的「检查间隔秒」是死配置，实际频率是声明值的 15 倍

- `config/fupan_config.ini`：`[视频监控] 检查间隔秒 = 900`
- Rust 侧：`grep -rn "检查间隔" zunzhe-core/src/` → **只出现在测试代码里**（`config.rs:1024`、`config_api.rs:219`），调度器从不读它。
- 实际节拍由 CLI 决定：`cli.rs:188-189` `#[arg(long, default_value_t = 60)] interval: u64`，`scheduler.rs` 每 60 秒一个 tick，视频检查挂在 tick 上。

**实测证据**（daemon 日志，B 站投稿接口调用间隔）：

```
04:35:36 → 04:36:45 → 04:37:59 → 04:38:06 → 04:39:07 → 04:40:16
```

最近 3000 行日志的字符串统计：

| 字符串 | 出现次数 |
|---|---|
| `412` | 694 |
| `352` | 166 |
| `error sending request` | 263 |

`doctor` 输出：`"source_health": {"failing": 2, "total": 4, "ok": false}`

**结论**：每 60 秒打一轮 B 站接口，把风控打出来了；四级兜底里前三级（官方 wbi / RSSHub / yt-dlp 前两次）基本全失败，靠最后一次 yt-dlp 兜住 30 条，但每轮要打 5 次外部请求。这是**配置项能被界面写、却没有任何代码读**造成的——比单纯的性能问题严重。

### S-3　daemon 主日志轮转把日志写到 `.log.1`，无上限增长

`~/Library/Logs/zunzhe/` 现状：

```
zunzhe-core.log     不存在
zunzhe-core.log.1   14,858,001 字节   最后写入 2026-09-17 12:36
```

而 `zunzhe-daemon.sh` 里明明写着 `exec ... run-daemon`，launchd 的 `StandardOutPath` 指向 `zunzhe-core.log`。

机制：`~/Library/LaunchAgents/zunzhe-healthcheck.sh` 的 `rotate_if_large()` 每 60 秒检查一次，用 `mv "$file" "$file.1"` 轮转。**`mv` 只改名、不改 launchd 持有的 fd**，daemon 继续往同一个 inode 写。第一次轮转后 `zunzhe-core.log` 就不存在了，后续检查 `[ -f "$file" ]` 为假直接跳过 → `.log.1` 变成实际的主日志，永远不再被轮转。

体量对得上：daemon 2026-09-10 16:33 启动，7 天 × 约 2MB/天 ≈ 14.8MB。

**最讽刺的是**，Rust 源码 `scheduler.rs:172-174` 的注释自己写明了这个坑：

> 主日志轮转交给外层启动器（start_rust_daemon 启动前 rotate）和 shell 看门狗，**不在 daemon 内 rename：tracing 持有打开句柄，进程内轮转会把新日志写到旧 inode，主日志看起来停更，反而破坏诊断。**

daemon 自己守住了，结果 shell 看门狗踩了同一个坑。**修法**：轮转只能放在 daemon 启动之前（或改成 `: > "$file"` 截断，让 launchd 的 fd 继续有效）。
